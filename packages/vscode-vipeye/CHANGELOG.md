# Change Log

## 1.1.427

- `__attribute__` no longer requires the file to `import t` / `import c`: the `t` / `c` module roots that `__attribute__(...)` desugars into are synthesized as **implicit module names** (zero-length, marked on the AST node — the compiler's attribute handling is AST-level and never checks symbol visibility either). When such a synthetic name cannot be resolved through the lexical scope chain, it falls back to the same-named binding in the built-in `builtins.vpi` stub; the fallback only applies to the desugared nodes, so a hand-written bare `t` / `c` in a file without the import still reports "未定义"
- **Analysis progress in the status bar**: while the language server builds the dependency graph and type-checks the workspace, the bottom-left status bar now shows `$(sync~spin) C:\xxx\1.vp (4/90) 4.44% loading...` — the file currently being analyzed, how many files have been processed out of how many, and the percentage. The worker reports per-file progress (throttled to one message every 50 ms) through a new `analysisProgress` background message and a new `viper/analysisStatus` notification; the client shows a left-aligned `StatusBarItem` and hides it as soon as analysis finishes (or when there is nothing to analyze). Previously the only feedback was the work-done progress bar for open-files analysis, which said nothing about which file was being processed, so a long full-workspace pass was indistinguishable from a hung server
- The **`static` modifier** is now supported (LSP side only; TransPyC/TransPyV are unchanged). It is a *soft* keyword: `static def f(...)` / `static fn f(...)` marks a function (recorded on `FunctionNode.d.viperModifier`, exactly like `virtual`) and `static x: T = v` marks a variable (the annotation is rewritten to `t.CStatic | T`, the same tree TransPyC's `_parse_type_ann` builds by inserting `t.CStatic` at the left of the union, so `static SECRET: int` renders as `static int`). Anywhere else `static` stays an ordinary identifier — `static = 1`, `static: int`, `static(x)`, `def f(static: int)` and `self.static` all parse as before. Its meaning is C's **internal linkage**: a static symbol **cannot be used across modules**. Referencing one from another module is reported as `'lib.helper' 是 static 符号，禁止跨模块使用（static 仅限定义模块内可见）` for both `mod.name` / `mod.fn()` (checked in the module member-access path) and `from mod import name` (checked on the import statement), while same-module references are allowed — the decision is made per declaration file, so a self-import is not flagged either. `static` is also offered by completion and highlighted as a modifier (`storage.modifier.viper`, matched in front of a `def`-family keyword or a type atom)
- The `f` prefix of an f-string is now highlighted as `storage.type.string.viper` (blue in the default dark theme) instead of being left unstyled. The rule matches the `r` / `u` / `b` / `f` prefix combination immediately preceding a quote, so it covers `f"..."`, `f'''...'''` and mixed spellings like `rf"..."`; a bare `r`/`f`/`b` identifier not followed by a quote is unaffected, and the string body keeps the usual `string.quoted.*` scope
- The **size of a fixed-length array type may be any integer constant expression** now: `part_types: [MAX_VOLUMES * MAX_PARTITIONS]uint8`, `part_lit: [MAX_VOLUMES * 2]uint8`, `part_left: [MAX_VOLUMES - 1]uint8` and `part_shift: [1 << 3]uint8` all parse and check cleanly. Two bugs made this fail before: the parser parsed the `[SIZE]` part while still flagged as a type annotation, so `_parseArithmeticTerm` deliberately stopped at the `*` (it is the C pointer suffix marker there) — the bracket was reported as "“[" 未关闭" and the leftover `* MAX_PARTITIONS]uint8` as "类型表达式中不允许使用解包运算符"; and the type evaluator then evaluated that arithmetic with `EvalFlags.TypeExpression`, reporting "类型表达式中不允许使用二元运算符". The size is now parsed as the value expression it is (the flag is cleared for its duration), and the evaluator allows arithmetic/bitwise operators in a type expression when **both operands are Viper integers** (the case the enclosing comment already described, e.g. `t.CArray[T, MAX_ORDER + 1]`); non-integer operands (`C1 + C2`) are still reported
- **`const` pointers are read-only for dereference assignment**: `lfn: const str` (`CConst | str`, i.e. `const char *`) now allows dereferencing — `*lfn` and `lfn[0]` evaluate to `char` — but writing through the dereference is reported as "不能给 const 指针的解引用赋值（"const str" 指向的数据为只读）". This covers **both** spellings, `*lfn = char(65)` (dereference) and `lfn[0] = char(65)` (**subscript assignment**), which share the same diagnostic. Previously the dereference itself was rejected with a bogus "类型"const str"不支持运算符"*"" (the `CConst` modifier in the union was mistaken for a non-pointer operand), and there was no read-only check at all. A non-`const` pointer (`buf: str`) still accepts `*buf = char(65)` and `buf[0] = char(65)`
- C type descriptors are **skipped** when checking iterability, so a `const` pointer can be iterated: `for ch in path:` with `path: const str` (and `const t.CPtr`) no longer reports "“CConst”不可迭代 / 未定义“__iter__”方法". The predicate now recognizes every Viper pointer (CPtr, `str`, `bytes`) rather than only `CPtr`, which is why `const str` had been missed — `CConst` fell through to the "not iterable" path
- The `static` modifier is **only** accepted at the start of a statement, before the variable name: `static memory_regions: memory_region* = None`, the spelling TransPyC's `_IsStaticModifier` understands. Writing it **inside the type annotation** (`memory_regions: static memory_region* = None`) is reported as a syntax error — `static 修饰符不支持写在类型注解里，请写成「static 变量名: 类型」（修饰符必须位于变量名之前）` — instead of being silently accepted (it used to desugar to the same `t.CStatic | T`, so the same meaning had two spellings and only one of them compiled). The descriptor is consumed and the remaining type is still parsed, so the same annotation no longer additionally reports `"static" is not defined`. `static` stays a **soft** keyword: it is special only when a type atom follows, so `static: int = 0`, `static = 1` and `def f(static: int)` are untouched
- `*args` is bound to the `va_list` **pointer** even when the file doesn't `import t`: the Viper var-arg rule used to look up `t.CPtr` through the source-visible `t` module only, so in a file like ViperOS `drivers/serial/uart/serial.vp` (no `import t`) it fell back to Python's `tuple` semantics and `viperlib.vsnprintf(&buf, 1024, fmt, args)` was reported as "无法将"tuple"类型的参数分配给函数"vsnprintf"中类型为"str"的参数"ap"". The lookup now falls back to the compiler built-in `rawptr` from `builtins.vpi` (= `t.CPtr`), the same mechanism `T*` annotations and `[SIZE]T` already use
- Indexing a C array now yields the **element type**, so member access on an element resolves: with `kbd_buf: [KBD_BUF_SIZE]usb_kbd_event`, `kbd_buf[i].modifier` used to report "无法解析类型上的成员"modifier"访问，对象可能未定义" and the member name got no semantic token at all (plain white). The CArray stub declares `class CArray(CType, Generic[T, N])` with `def __getitem__(self, index: int) -> T`, but Viper-side `TypeVar(...)` does not produce substitutable type variables (the class's type parameters end up as synthesized `__P0` / `__P1`), so the return type never became concrete. The Viper index path now reads the **first type argument** directly (C semantics: `arr[i]` has the element type), the same way the `CPtr[T]` branch reads `priv.typeArgs[0]`; this covers both `[SIZE]T` and the explicit `t.CArray[T, N]` spelling, and works for a union base too (`CArray[T, N] | t.CExport`)
- **`export` / `extern` on variable declarations** are now supported: `export gdt: [7]gdt_entry = []`, `export tss_buf: [104]uint8` and `extern ext_flag: int`. The variable form is told apart from the function form (`export def f()` / `export f(...)`) by the third token — `:` is a variable (type annotation), `(` / `[` is a function, the same criterion as TransPyC's `_is_export_extern_var`). They desugar exactly like TransPyC's `_parse_export_extern_var`: `export NAME: T [= v]` becomes `T | t.CExport` (bare-named definition, **no module SHA1 header**), `extern NAME: T` becomes `T | t.State` (= `CExtern | CExport`, declaration only). An **initializer is allowed for `export` but rejected for `extern`** — `extern a: int = 1` reports "extern 变量声明不能带初始值（符号定义在外部）", matching the compiler's fail-fast. Storage-class markers render as a prefix qualifier (`export CArray[gdt_entry, 7]`, `extern int`), and the marker is treated as a modifier everywhere else: in the `Struct | CPtr` fold (so `extern p: t.CPtr` stays a pointer instead of degrading to `CPtr[State]`), in the union index access, and as a CArray element access (so `gdt[i].access` still resolves to `uint8` and the zero-initializer `= []` is accepted)
- `[SIZE]T` array annotations no longer require the file to `import t`. The parser desugars `coroutines: [8]Coroutine` into a synthetic `t.CArray[Coroutine, 8]` member access; when that synthetic `t` could not be resolved through the lexical scope it silently degraded to `Unknown`, so the whole array annotation collapsed and `m.coroutines[i].rsp` reported "无法解析类型上的成员“rsp”访问" with `rsp` getting no semantic token at all (rendered unhighlighted, no jump-to-definition). The synthetic `t` now falls back to the `t` module bound in the built-in `builtins.vpi` scope — the same mechanism `T*` uses for `rawptr` and `__attribute__(...)` uses for its implicit module roots — so a file without `import t` still gets the real `CArray[Coroutine, Literal[8]]` and the element's member resolves
- Attribute names inside `__attribute__(...)` are highlighted **structurally**, so a name that the compiler supports but that isn't declared in the `attr` class still colours like the declared ones. `stackrealign` (supported by TransPyV's code generator — `FuncGenBase.vp` maps it to the LLVM `"stackrealign"` attribute — and used by ViperOS `VKernel/Kernel/main.vp`) is declared in neither `t.py` nor the `t.vpi` stub, so `t.attr.stackrealign` used to be unresolvable: the name got no semantic token (rendered unhighlighted) and the file was additionally flagged with "无法访问类"type[attr]"的属性"stackrealign"". The parser now marks the synthesized attribute-name node, the semantic token provider colours it as `function` (exactly like a declared attribute such as `section` / `aligned` / `naked`), and the member-access diagnostic is suppressed for these names — the compiler silently drops unknown attributes rather than rejecting them, so reporting them was a false positive. Declared names keep resolving through `t.attr` as before, so hover and jump-to-definition still work for them
- `__attribute__(...)` **completion and hover** now list attribute names that the compiler supports but that the `attr` class doesn't declare, instead of only mirroring `t.attr`. `stackrealign` is offered by typing inside the parentheses and appears in the hover list of available names; the list is a single shared union (`viperAttributeUtils.getViperAttributeNames`) of `t.attr`'s declared names plus these extra names, so completion and hover cannot drift apart. Declared names keep coming from the stub symbol table (so they still show their signature and support jump-to-definition)
- Pointer-to-pointer implicit conversion is now **strict** instead of "same level is always allowed". A pointer converts implicitly to another pointer only when the **level** matches **and** the pointee is compatible: either side being `void*` / undetermined (`rawptr`) always allows it, identical pointees are allowed, two basic (numeric scalar) pointees follow the very same rules as the values themselves (`uint32* → uint64*` and `uint32* → uint16*` are allowed because integers convert in every direction; `float* → int*` is still reported), and for **structs** only a conversion **within the same inheritance hierarchy** is allowed — the upcast (`Sub* → Node*`; `memhub` / `requests` depend on `MemBuddy* → MemManager*`) as well as the downcast (`AST* → Call*`; `CallGenDispatch.vp:824` passes an `ast.AST*` into a `rawptr[ast.Call]` parameter and Viper pointers carry no static type at runtime, so the reinterpret is routine), while two unrelated structs (`Node* → Other*`) and a struct↔basic mix (`Node* → uint64*`) are rejected. Single-level pointers also convert to and from `void*` (`t.CVoid`) in both directions, while multi-level ones still don't (`Node** → void*` is reported). `&x` / `*x` already produced the right types (`&x` is `T*` for `x: T`, `T**` for `x: T*`; `*x` is `T` for `x: T*`) and now take part in these checks too — `a(&x)` with `x: Node*` (a `Node**` into a `void*` parameter) is reported as before, and so is `a(&x)` where the parameter is a single-level pointer
- **A bound on a generic class's type parameter** (`novirtual class GSList[T: GSListNode]:`) is now honoured, so the generic method bodies that rely on it check cleanly — `includes/linkedlist.vp`'s `append` used to report "无法为类"GSList[T@GSList]*"的属性"Head"赋值 / "GSListNode*"不可分配给"rawptr[type[T@GSList]]"" and "无法为类"GSListNode*"的属性"Next"赋值 / 属性"Next"未知". Three missing pieces had to be filled in: (1) the `CPtr` dereference (member access, attribute-access override and subscript) now concretizes a **TypeVar pointee to its bound**, otherwise `self.Tail.Next` looked for `Next` on `CPtr[T]` instead of on `GSListNode`; (2) assigning a **generic type-parameter value to `CPtr[T]`** is now allowed, mirroring the existing "class instance → `CPtr[T]`" rule (in Viper a class-typed value *is* a pointer), which covers `self.Head = node` / `self.Tail = node`; (3) when the member type resolved on an unspecialized generic base degrades to `CPtr[type]` (a pointer to a class object, i.e. "target type unknown"), it is treated like `rawptr` / `void*` and allowed. Removing the bound keeps the error (an unbounded `T` has no `Next`), so the bound is what makes the generic body type-safe. TransPyC is unaffected — its parser already accepts and skips `[T: bound]`
- Pointers to the **variants of a `t.REnum`** are now compatible with pointers to the REnum root (and vice versa), so `rawptr[LLVMType.Ptr]` converts to `rawptr[LLVMType]` instead of being reported as "无法将"rawptr[Ptr]"类型的参数分配给函数"build_load"中类型为"rawptr[LLVMType]"的参数"ty"". The variant classes are nested inside the root class's suite (`class LLVMType(t.REnum): class Ptr: ... / class Int: ...`) rather than derived from it, so `isDerivedFrom` could not see the relation — yet TransPyV only emits a bitcast between the two addresses, and `match`-variant narrowing already rewrites `CPtr[LLVMType]` into `CPtr[LLVMType.Ptr]` (see `narrowTypeBasedOnClassPattern`), which is exactly what llvmlite does: `CallGenCall.vp` narrows `lb_inner: rawptr[LLVMType]` through a nested `case llvmlite.LLVMType.Ptr(lb_inner2)` and passes it straight back to `build_load(builder, ty: rawptr[LLVMType], ...)`. The relation is detected by full-name nesting (`'LLVMType.Ptr' ⊂ 'LLVMType'`, the same criterion the narrowing uses) together with the root's MRO containing `REnum`; two different variants (`Ptr* → Int*`) and a mix with an unrelated struct are still reported
- Assigning a **plain function to a method slot of a `virtual class`** is now accepted: `serial0_file.open = serial0_open` (ViperOS `devfs.vp`, where `devfs_file` is a `virtual class` and `serial0_open(self: rawptr, path: const str, flags: int) -> int` is a module-level function) used to be reported as "无法为类"devfs_file"的属性"open"赋值 / 参数名称不匹配: "path" versus "self" / 额外参数 "flags"". Such an assignment writes a **vtable slot**, and the compiler (TPC `HandlesAssign` / TransPyV `CallGenVt._write_vtable_slot`) just bitcasts the function to `i8*` and stores it — it never validates the signature or `self` — whereas the language server compared the *bound* method type (with `self` already stripped), so the explicitly written `self` looked like a spurious extra parameter. The check now follows the vtable semantics: the class must be a `virtual class` (`virtual class X` or `@t.CVTable class X`), the member must be a method declared in it, the assigned function's `self` must be a generic pointer (`rawptr` / `t.CPtr`) or a pointer to that class itself or one of its base classes, and every remaining parameter must match by name and type with an identical return type (`*args` / `**kwargs` are not compared, so they may be present on either side). Everything else — a non-virtual class, `self` that isn't such a pointer, or a parameter/return mismatch — is still reported

## 1.1.426

- **Type descriptors**: `const` / `volatile` may prefix any type annotation — `a: const int`, `b: volatile int`, `def f() -> volatile int`, `p: const t.CPtr`, `q: const int*`, in parameters, return types, class members and type aliases. Both are **hard keywords** now (reserved words): the only legal use is a type-annotation prefix, anything else (`const = 1`, `a: const` with no type) is reported as a syntax error with a dedicated message. They desugar in the parser into the equivalent type-set annotation `CConst | T` / `CVolatile | T`, so they weigh exactly the same as the hand-written form in assignment compatibility, operator handling and diagnostics — no second modifier mechanism. The desugared `CConst` / `CVolatile` names live in the built-in `builtins.vpi` stub, so no `import t` is required
- `const T*` is now `(CConst | T)*` → `CConst | CPtr[T]`, i.e. a pointer to the described type, matching the `CConst | CChar | CPtr` (const char *) spelling used by TransPyC. The pointer suffix is always applied at the outermost level, so the result no longer depends on whether the `*` is followed by an end-of-line or by more source (a newline used to make the star attach at a different level, leaving the annotation as `Unknown`)
- `T*` / `&x` no longer require `import t`: when the file doesn't import the `t` module, `CPtr` falls back to the compiler built-in `rawptr` from `builtins.vpi`. Previously such files got `type[int] is not supported for operator "*"` and an `Unknown` type
- `|` combinations that mix a type descriptor with an **instance**-form type (e.g. `t.CConst | int*`, whose right operand evaluates to `CPtr[int]`) are now treated as a type-set union instead of falling through to `__or__` and degrading to `Unknown`
- Type descriptors are rendered as a **prefix qualifier** instead of a union member, so the internal representation never leaks into hovers or diagnostics: `a: const int*` shows `const rawptr[int]` (not `CConst | rawptr[int]`), `a: const int` shows `const int`, and `a: const volatile int` shows `const volatile int`. Storage-class descriptors get the same treatment (`static` / `register` / `auto` / `inline` / `extern`)
- Type descriptors no longer appear as the pointee of a pointer: `(CConst | int)*` evaluates to `CConst | CPtr[int]` rather than the "union of pointers" `CPtr[CConst] | CPtr[int]`
- `t.CVolatile` is handled everywhere `t.CConst` already was (type-set subscript, iteration, member access, string-literal assignability, `Struct | CPtr` folding), so `volatile` behaves symmetrically with `const`
- New **`inline while cond:` / `inline for x in y:`**: the `inline` modifier is accepted on loop statements (it is a code-generation hint, so no additional type semantics — the loop is parsed as a plain `while` / `for`), and `inline` is highlighted as a modifier. Using `inline` anywhere else still reports "must be used with 'def'"
- `const` / `volatile` are highlighted as type modifiers
- New built-in C basic type names `uint` (`t.CUnsignedInt`) and `uchar` (`t.CUnsignedChar`), declared in the built-in `builtins.vpi` stub. Any Viper project resolves them without configuring `includes` — `uint` already exists in TransPyC's `includes/builtins.vp` but was missing from the stub, so it was reported as undefined in setups where that file cannot be located; `uchar` is new in both places
- New **`virtual` / `novirtual` declaration modifiers** for vtable control, equivalent to the `@t.CVTable` / `@t.NoVTable` decorators: `virtual class X` (polymorphic vtable) and `novirtual class X` (flattened, no vtable) are recorded on the class node, and `virtual def f(...)` / `novirtual def f(...)` mark individual methods. Placement is enforced: `virtual def` must be inside a `class` or `virtual class` (rejected inside a `novirtual class`, at module level, or nested in a function body), and `novirtual def` must be inside a class of any of the three forms. Using either modifier without `class` / `def` reports a dedicated error, they work after decorators too, and both are highlighted as type modifiers
- Two-level pointer casts work now: `(T**)x` / `(T**)(x)` evaluate to `CPtr[CPtr[T]]` (e.g. `slot_l: ast.AST** = (ast.AST**)(uint64(data_l) + li_l * elem_sz_l)`, whose element access `slot_l[0]` yields `ast.AST*`). The `T**` AST is a nested unary `*` pair whose outer operand is already the `CPtr[T]` instance produced by the inner one; in a value context that was read as a **dereference**, collapsing the cast target to `T` (reported as "object of type 'T' is not callable") and losing the second pointer level. Pointer-type suffixes marked by the parser are now always evaluated as type expressions, so `(T*)x` / `T*(x)` are unaffected
- Bare C-style inline-asm and LLVM-IR builtins, so the C spelling can be used verbatim without any import or module prefix: **`__asm__(...)`** (same as `c.Asm` / `Asm`), **`asminp(...)`** / **`asmout(...)`** (same as `c.AsmInp` / `c.AsmOut`), **`__llvmir__(...)`** (same as `c.LLVMIR` / `LLVMIR`) and **`irinp(...)`** / **`irout(...)`** (same as `c.LInp` / `c.LOut`), plus **`ASM_DESCR`** (same as `t.ASM_DESCR`, so `ASM_DESCR.REG_ANY` / `ASM_DESCR.CLOBBER_RDX` resolve). All of these are declared in the built-in `builtins.vpi` stub except `ASM_DESCR`, which is re-exported there as `from t import ASM_DESCR as ASM_DESCR` (a stub re-export must use the redundant-alias form). The existing `Asm` / `AsmInp` / `AsmOut` / `LLVMIR` / `LInp` / `LOut` names and the `c.*` / `t.ASM_DESCR` spellings keep working
- `X | t.CPtr` now folds to a pointer-to-`X` even when `X` is itself a pointer: `HANDLE | t.CPtr` (with `HANDLE = VOIDPTR = t.CPtr`, i.e. void*) is `void**`, not `void*`. Both operands used to evaluate to the very same type (`type[CPtr[Unknown]]`), so the union collapsed into a single-level pointer and `&handle` (void**) was rejected — e.g. `w32.win32file.CreatePipe(&stdout_read, &stdout_write, &sa, 0)`, whose parameters are declared `HANDLE | t.CPtr`, reported "跨级指针隐式转换不允许" (a false positive: `LPHANDLE` really is `HANDLE*`). `createUnionType` now decides this syntactically: when the right operand is the bare `CPtr` / `rawptr` class and the left operand already is a pointer type, the left operand is wrapped (`CPtr[X]`). Struct / void / str operands keep their previous behavior (`Scheduler | t.CPtr` → `CPtr[Scheduler]`, `CVoid | t.CPtr` → void*, `str | t.CPtr` → i8**), and genuine level mismatches (void** → void*) are still reported
- Viper's own keywords are now offered by completion: the hard keywords **`define`** (macro function, same as `def`), **`const`** / **`volatile`** (type-descriptor prefixes) and the soft keywords **`typedef`**, **`inline`** / **`export`** / **`extern`** / **`virtual`** / **`novirtual`**, **`enum`** / **`rnum`** / **`union`** / **`struct`**, plus the `def` aliases **`fn`** / **`fun`** / **`func`** / **`function`**. They are absent from CPython's keyword table, so they used to be invisible in the suggestion list even though the parser accepts them (the TextMate grammar already highlighted them). `completionProvider`'s `Keywords` namespace now merges a Viper list into both the full and the expression-only keyword sets
- New **"Count Project LOC"** command (`viper.countLines`): right-click a `.vpj` in the Explorer → the project's `source_dir` (usually `App`) is scanned recursively and every **known language** is counted. A **`Viper LOC` Webview panel** opens *before* the scan and shows a **determinate progress bar** (files collected first, then processed `N / M` with the current file), and once done renders the report: KPI cards (files, total / code / comment / blank lines, **comment rate**, **average line length**, characters), a **stacked bar chart** per language (code / comment / blank segments, scaled to the largest language), a **language filter** (checkboxes that re-compute the KPIs, chart and table), and a detail table with a totals row. The same report is also written in plain text to the `Viper LOC` output channel for copying. Known languages follow the extensions this extension registers (`.vp`, `.vpi`, `.vpnci`, `.vpj`) and, as requested, `.def` files are supported too (module-definition `;` line comments, C-style `//` line comments and slash-star block comments are all recognized; block comments that span lines are counted as comments). The project's `build_dir`, hidden directories, `node_modules`, `.git` and `__pycache__` are skipped, and symlinks are not followed
- `T*(x)` casts now accept a bare name that resolves to a **module** when that module defines a class with the same name, as in `import bootinfo` plus `bootinfo.vp`'s `class bootinfo` — the spelling ViperOS uses for `BootInfo = bootinfo*(saved_rdi)` in `VKernel/Kernel/main.vp`. TransPyC's struct registry is keyed by short name, so the plain name picks up the class there; Vipeye evaluated it as the module instead, the cast fell through to arithmetic and reported `类型"Module("bootinfo")"和"ulong"不支持运算符"*"`. It now folds to `CPtr[bootinfo]`, identical to the qualified `bootinfo.bootinfo*(saved_rdi)` / `bootinfo.memory_map_entry*(saved_rdi)` spellings. A module without a same-named class is not turned into a cast, so the genuine operator error is still reported
- `T*(x)` is now parsed as a **call** (`T*(x)[i]` / `T*(x).f` therefore work), matching TransPyC's `_AtPtrSuffixCall`: when a type atom (`Name` / `member access` / `subscript`) is followed by a run of `*`/`**` and then `(` with **no whitespace anywhere in between**, the run is consumed as a pointer-type suffix and the `(` becomes the call trailer — the same tree `(T*)x` already produces. This fixes `uint32*(info.vendor_id)[0] = res.ebx` in ViperOS `drivers/core/cpu/cpu.vp`, which was read as `uint32 * (info.vendor_id[0])` and reported "表达式不能是赋值目标" (the whole multiplication sat on the left of `=`); the cast now yields `CPtr[uint32]`, the subscript yields `uint32`, and the assignment is accepted. Real multiplications keep multiplying: `a * (b)`, `(a) * (b)`, `(a)*b`, `n*(m - 1)` and `2 * 3` are unaffected (whitespace or a non-type-atom base), and `(T*)[i]` stays a subscript
- **Duplicate declaration** of a module-level variable inside a function is now an **error (TypeError)**, matching TransPyV's `AssignGenMixin` check: when the module already declares a runtime variable `x` (`x: T = ...`), a **type-annotated** declaration of the same name inside a function fails *unconditionally* — both without a `global` statement (it would shadow the global as a local) and **with** one (the annotation duplicates the existing global declaration). Type equality is deliberately not considered. The only legal spellings stay: `global x` + an **un-annotated** `x = v` assignment, or a differently-named local. Scope is function-only — module-level re-annotation, class members, `CDefine` macro constants (no global storage), `CTypedef` aliases and same-named functions/classes are not flagged; the diagnostic is only produced when the name really is a module-level variable. Verified against the real tree: `TransPyV/App`, `VET/App` and `includes` (147 files) have **zero** violations, while the TPC-compiled ViperOS kernel has 14 in `VKernel/Kernel/paging/paging.vp` (L99–L190 re-annotate `pdp` / `pd` / `pt` right after `global pdp, pd, pt`), which TransPyV rejects as well
- **`__attribute__`** is now supported in both spellings Viper uses (LSP side only; TransPyC/TransPyV are unchanged). As a **decorator**, `@__attribute__(section(".text.wo"), always_inline)` desugars into `@c.Attribute(t.attr.section(".text.wo"), t.attr.always_inline)` — the same tree TransPyC's `_DesugarMagicAttribute` produces, so it works for `class` and `def` alike and no second mechanism is introduced. As a **modifier**, `a: __attribute__(section(".x")) const int = 1` desugars into the type-set annotation `t.attr.section(".x") | (CConst | int)`, i.e. the same family as `const` / `volatile` (it must be followed by a type, one layer of parentheses only — not GCC's `__attribute__((...))`), and it composes freely with `const` / `volatile` in either order. Attribute names in the parentheses are offered by completion, listed from the `attr` class declared in the `t` stub
- Attribute markers in a type annotation (`T | t.attr.section(".x")`, `T | t.attr.llvm.nounwind`, and the markers the parser synthesizes from `__attribute__(...)`) are now evaluated as the modifier `t.CAttr` instead of leaking into the annotation as a union member. Previously `t.attr.llvm.nounwind` stayed the class `nounwind` — itself a union member, so `P: t.CInt | t.attr.llvm.nounwind | t.attr.llvm.nobuiltin` displayed as `CInt | nounwind | nobuiltin`, `p + 1` reported "运算符不支持" and `V[0]` reported "类型"nounwind"上未定义"__getitem__""; and `t.attr.section(".x")` (a *call*) was rejected with "类型表达式中不允许使用调用表达式". `CAttr` joins the existing C-modifier family, so operators, subscripts, assignment compatibility and rendering all skip it by the same rules as `CConst` / `CVolatile`, and the property names (`section`, `always_inline`, `nounwind`, …) resolve against the `t` stub for jump-to-definition and hover
- New **value-position `volatile` prefix**: `a: int = volatile f()` and `b: Settings = volatile Settings()` mark a call (function call or struct construction) as volatile for code generation — the expression keeps the call's own type, TransPyC / TransPyV are not involved. Only a call may follow it (one is reported otherwise), and the bare uses `volatile = 2` / `const = 1` still report a syntax error
- `__attribute__` is highlighted as a type modifier (same scope as `const` / `volatile`): the TextMate grammar matches it when followed by `(`, in both the decorator and the modifier spelling
- `__attribute__` is also offered by completion (typing `__a` lists it) and **hovering inside `__attribute__(...)`** shows the full list of available attribute names (`section` / `aligned` / `always_inline` / `weak` / …), taken from the `attr` class of the `t` stub. Both share one helper (`viperAttributeUtils`) for locating the parentheses and enumerating `t.attr`, so the completion list and the hover list cannot drift apart
- Lowercase **`callable[[A, B], R]`** is now supported in a type annotation and means exactly `t.Callable[[A, B], R]` — all three spellings (`callable[...]`, `Callable[...]`, `t.Callable[...]`) and all the usual argument forms (`callable[[int, str], bool]`, `callable[..., bool]`, `callable[[], bool]`, as a parameter, return or variable annotation) evaluate to the same callable type. The parser rewrites the bare name `callable` to `Callable` **only in type-annotation position**, so the built-in function is untouched: `callable(x)` / `if callable(x):` still behave as before. `Callable` is declared in the built-in `builtins.vpi` stub (`Callable: t.CTypedef = t.Callable`, next to `rawptr` / `CConst`), so no `import t` is required. Previously `callable[[int], bool]` silently degraded to the type of the `callable` *function* (the Viper-dialect rule that ignores explicit type arguments on a callable), and bare `Callable` was reported as undefined

## 1.1.425

- New `typedef T1 = T2` statement, fully equivalent to `T1: t.CTypedef = T2`. It desugars in the parser into the same annotated-assignment tree (synthetic zero-length `t.CTypedef`), so binding, type evaluation, hover and semantic highlighting all behave identically — and it works without the file having to `import t`. `typedef` is a soft keyword, so `typedef = 1` / `typedef(x)` still parse as before. `typedef` is also highlighted as a declaration keyword now
- `(T)x` casts are accepted alongside `(T*)x`: when the parenthesized expression is a type atom (a name, `t.CInt`, a subscript, or `T*`) and an operand follows, it is normalized into the equivalent `T(x)` call. `(T*)[i]` stays a subscript and `(a)*b` stays a multiplication

## 1.1.424

- C-style casts now accept the pointer spellings used by TransPyC: `(T*)x`, `(T*)(x)` and `T*(x)` all evaluate to the pointer type (`CPtr[T]`). Inside parentheses or call arguments `T*` is read as a pointer *type* when the operand is a type object, and a binary `*` whose left operand is a type object is read as a cast — so `2 * 3` / `offset * 2` still multiply. `(T*)a + b` groups as `((T*)a) + b`, and `(T*)[i]` remains a subscript

## 1.1.423

- Parser: the C pointer suffix (`T*` / `T**`) is now recognized in call arguments, not only inside type annotations, so `va_arg(ap, int64*)` / `short*` / `int*` (as used by TransPyC's `viperlib.vp`) parse correctly. Real multiplication and power expressions (`a * b`, `a ** b`, `N * 2`) are unaffected
- `str | t.CPtr` / `bytes | t.CPtr` now fold to `CPtr[str]` / `CPtr[bytes]` (`i8**`, e.g. `argv`), and indexing such a pointer yields the pointee (`str` / `bytes`) instead of `char` — fixes `token: str = entry[0]` being reported as `char` not assignable to `str` (`argparse.vp`)
- C-style casts targeting a plain built-in type are accepted: `char(addr, t.CPtr)` (used by `memhub.vp` / `requests.vp`) no longer fails `char.__new__`'s `base: SupportsIndex` overload. The rule requires the second argument to be a type object, so Python's `int("12", 16)` is unaffected
- `flowChartCommand` now passes a `CancellationToken` to `AnalyzerService.run`, fixing a TS2554 error that blocked five test suites
- Test maintenance: the stale `ord` signature assertion was updated (TransPyC now declares `def ord(s: char) -> int`), and the `AssignGenMixin.vp` narrowing guard no longer hard-codes line numbers, so it survives source drift

## 1.1.422

- `str` / `bytes` iteration now yields `char` as well: `for ch in s` and `Iterable` / `Iterator` argument inference (`enumerate`, `zip`, `map`, `filter`, `reversed`, `sorted`, `list()` …) bind the element type to `char`, matching subscript `s[i]` and dereference `*s`. The old `t.CChar`-aliased `int` construction is removed

## 1.1.421

- `s[i]` on `str` / `bytes` now yields `char` (`i8`) instead of `t.CChar`, matching the dereference result of `*s` (the two remain implicitly convertible). Covers both the plain subscript path and the type-set subscript path (e.g. `CConst | str | CPtr` style annotations). Iteration and `Iterable` inference were unified in 1.1.422

## 1.1.420

- Pointer semantics for `str` / `bytes` (both are C `char*`, `i8*`) now cover pointer arithmetic and writes, matching the dereference support added earlier: `p + n`, `p - n` and `n + p` return the pointer type instead of reporting `reportOperatorIssue`, and `*p = v` is accepted as an assignment target. Subscript access `p[i]` was already supported

## 1.1.419

## 1.1.418

- **Built-in C basic type names**: `long` (`t.CLong`) and `longlong` (`t.CLongLong`) are now built-in typedefs, mirroring the compiler's `_CNAME_ALIAS` table (`char`, `short`, `long`, `unsigned` and friends are language built-ins that need no import). C's `long long` cannot be spelled with a space, so Viper writes `longlong`; the unsigned form stays available as `t.CUnsignedLongLong`

## 1.1.417

- **Built-in C integer typedefs**: `sizet`, `size_t`, `uzt`, `int8`–`uint64`, `intfast*`/`uintfast*`, `intleast*`/`uintleast*` are now declared in the built-in `builtins.vpi` stub, mirroring the compiler's `includes/builtins.vp`. Any Viper project resolves them without configuring `includes`, which fixes `uint32` (and the rest) being reported as undefined in setups where the project-level `builtins.vp` cannot be located — that lookup depends on the workspace root and the set of opened files, so the same project could behave differently across editors

## 1.1.416
